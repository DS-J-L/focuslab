# FocusLab 평가 및 개선 우선순위

평가일: 2026-10-20 · 대상: 현재 로컬 작업 트리, Windows/Python 3.11 개발 환경

## 종합 판단

**유용한 프로토타입이다. 다만 일반 사용자 배포 전에는 동의 철회와 통계·내보내기 일관성을 먼저 수정해야 한다.**

목표별 세션, 자동 활동 기록, 관찰 근거, 사용자 정정, 로컬 저장이 연결되어 있다. 반면 자동 기록과 수동 집중 세션의 제품 경험은 아직 분리되어 있고, 실제 사용자 라벨로 판정 성능을 검증한 결과는 없다. 기능 추가보다 기존 기록을 믿을 수 있게 만드는 작업의 우선순위가 높다.

평가는 소스, 기존 활동 화면 이미지, 오프스크린 GUI를 포함한 테스트 및 합성 데이터 재현을 바탕으로 했다. 실제 카메라 촬영, 장시간 실사용, 설치 파일 배포 및 외부 경쟁 제품 비교는 수행하지 않았다. 앱 구현 코드는 변경하지 않았다.

## 잘된 점

- **수집 최소화와 통제:** 카메라·자동 기록·브라우저 관찰의 선택을 나누고, 원본 영상·창 제목·키 입력 내용을 저장하지 않는 구조다. 다만 진행 중인 세션의 동의 철회에는 아래 결함이 있다.
- **설명과 정정:** 판정 근거, 미분류, 사용자 정정, 앱·사이트별 규칙이 있어 오판을 사용자가 이해하고 바로잡을 수 있다.
- **관찰의 한계 인식:** YouTube 등 다목적 사이트를 미분류로 남기고, 머리 방향만으로 집중 상태를 확정하지 않는 방향이 적절하다.
- **구조와 검증 기반:** UI·서비스·규칙·저장소가 분리되어 있고, 모의 센서, DB 마이그레이션, 비정상 종료 복구 및 브라우저 프로토콜 테스트가 있다.
- **운영 비용을 고려한 기록 방식:** 이벤트 훅과 폴링, 구간 병합, 배치 저장을 사용한다. 기존 성능 문서는 측정 범위와 한계를 함께 적고 있다.

## 재현한 결함

### 1. P0 — 동의 철회가 진행 중인 세션의 관찰을 멈추지 않는다

근거: [settings_page.py](../src/focuslab/ui/settings_page.py)의 `_toggle_camera`, `_toggle_activity`, [context.py](../src/focuslab/ui/context.py)의 센서 팩토리, [session_service.py](../src/focuslab/services/session_service.py)의 `start`, `tick`.

설정은 동의 플래그만 변경한다. 서비스는 시작 시 생성한 카메라·PC 관찰 소스를 계속 사용하며, 매 틱에서 동의를 다시 확인하지 않는다.

**재현:** `demo=False`인 컨텍스트에 모의 카메라와 추적 가능한 PC 관찰 소스를 주입했다. 세션 시작 후 실제 설정 페이지의 두 철회 동작을 호출하고 다음 틱을 진행했다.

```text
consents_after_revoke = False False
camera_status_after_revoke = RUNNING
camera_stop_calls = 0
activity_sample_calls_after_revoke = 1
persisted_app_after_revoke = audit-app.exe
```

실제 카메라나 OS 활동을 읽지 않고 서비스 연결 경로를 검증한 결과다.

**개선:** 동의 변경을 서비스의 관찰 중지 동작과 연결한다. 카메라 철회 시 장치를 해제하고 미리보기·최근 관찰값을 지운다. PC 관찰 철회 시 현재 소스를 관찰 불가 소스로 교체한다. 일시정지 후 재개해도 철회한 관찰이 다시 켜지지 않아야 한다. 자동 기록 동의는 별개이므로 각 동의의 적용 범위도 명확히 안내한다.

**완료 기준:** 세션 실행 중·일시정지 중 각각 철회한 뒤 센서 호출과 해당 데이터 저장이 중단되고, 재개 시에도 유지된다.

### 2. P1 — 조회 기간과 순서에 따라 저장된 자동 세션이 중복된다

근거: [activity_service.py](../src/focuslab/services/activity_service.py)의 `rebuild_auto_sessions`, `activity_report`.

조회 범위에 맞춰 활동 구간을 자른 후 자동 세션을 저장하지만, 기존 행은 시작 시각이 조회 범위 안에 있는 것만 삭제한다. 범위 시작 전에 시작해 안으로 이어지는 기존 세션은 남는다.

**재현:** 자정 전 10분부터 자정 후 10분까지 이어지는 `code.exe` 활동 하나를 넣었다.

```text
이틀 조회 후 저장: [23:50–00:10]
다음 날 조회 후 저장: [23:50–00:10, 00:00–00:10]
원본 활성 시간: 20분
저장된 자동 세션 활성 시간 합계: 30분
```

현재 화면의 원본 활동 합계가 모두 중복된다는 뜻은 아니다. 저장된 파생 세션과 이를 읽는 전체 JSON 내보내기에 문제가 생긴다.

**개선:** 자동 세션의 기준 구간을 조회 화면과 독립적으로 정의하고, 화면에서는 그 결과를 잘라 표시한다. 범위별 재계산을 유지한다면 경계에 걸친 기존 세션과의 교체 정책을 함께 설계해야 한다.

**완료 기준:** 하루→7일→하루, 30일→하루 등 조회 순서를 바꿔도 동일한 원본·규칙의 자동 세션과 내보내기가 같고 중복되지 않는다.

### 3. P1 — 활동 화면을 열지 않으면 전체 내보내기에 자동 세션이 빠진다

근거: [export_service.py](../src/focuslab/services/export_service.py)의 `activity_dict`는 `stored_auto_sessions`만 읽는다. 자동 세션 재계산은 활동 조회 경로에서 수행한다.

**재현:** DB에 20분 활동을 넣고 활동 보고서를 호출하기 전에 `activity_dict`를 실행하면 `automatic_sessions`는 0개였다. 보고서를 호출한 뒤에는 1개였다. 규칙 변경 후 화면을 다시 열지 않은 경우에도 오래된 결과를 내보낼 수 있는 구조다.

**개선:** 화면 방문 여부와 무관하게 내보내기 서비스가 최신 원본·규칙에 맞는 결과를 생성하거나, 버전이 검증된 파생 데이터를 사용하게 한다. 2번과 함께 수정하는 것이 좋다.

**완료 기준:** 기록 후 바로 내보내기, 활동 화면 방문 후 내보내기, 정정 직후 내보내기의 결과가 각각 최신 상태와 일치한다.

### 4. P1 — 자정을 넘긴 수동 세션을 시작한 날짜에 전부 집계한다

근거: [export_service.py](../src/focuslab/services/export_service.py)의 `daily_totals`, [home_page.py](../src/focuslab/ui/home_page.py)의 `refresh`.

일별 리포트는 세션 시작 날짜로 전체 샘플을 묶는다. 홈도 오늘 시작한 세션만 선택한다.

**재현:** 10월 19일 23:59:59와 10월 20일 00:00:00에 해당하는 `ON_TASK` 샘플을 하나씩 넣었다. `daily_totals`는 19일에 2초, 20일에 0초를 반환했다. 기대값은 각각 1초다.

**개선:** 저장된 샘플의 실제 시각 `at_ms`를 현지 날짜로 나눠 집계한다. 오래된 데이터와 시각이 없는 공백 샘플의 처리 기준도 정의한다. 홈 집계의 최근 50개 제한도 최근 목록 표시와 분리한다.

**완료 기준:** 자정 통과·일시정지·재개를 포함한 세션의 날짜별 합계가 전체 합계와 일치한다.

### 5. P1 — 일부 구간만 촬영해도 구간 전체를 카메라 관찰 시간으로 표시한다

근거: [stats.py](../src/focuslab/activity/stats.py)의 `compute_stats`, [camera_overlay.py](../src/focuslab/activity/camera_overlay.py)의 `CameraOverlay`, [activity_page.py](../src/focuslab/ui/activity_page.py)의 작업 시간 카드.

`has_camera`가 참이면 해당 활동 구간의 전체 길이를 `camera_covered_ms`에 더한다.

**재현:** 10분 활동 구간에 카메라 관찰 1초만 연결했는데 `camera_covered_ms`는 600초였다.

**개선:** 관찰 샘플의 실제 시간 구간과 활동·조회 범위의 교집합으로 커버리지를 계산한다. 카메라 꺼짐·실패·관찰 불가의 구분도 유지한다.

**완료 기준:** 10분 활동 중 1초만 관찰했다면 1초로 표시하고, 일부만 포함한 날짜·기간 조회에서도 부풀리지 않는다.

| P1 | 자동 기록만 사용하는 사람은 홈의 수동 세션 지표가 0으로 보여 기록 여부를 혼동할 수 있다. | 홈에서 자동 기록 상태·오늘의 활동 요약·집중 세션 시작을 함께 제공한다. 카드마다 자동 기록인지 수동 세션인지 표시한다. |
| P1 | ‘실제 활성 사용’은 입력 기반 활성 시간이다. 입력 없이 강의를 듣거나 읽는 시간도 자동 기록에서는 유휴가 될 수 있다. ‘작업 시간’도 고정 카테고리 합계다. | ‘입력 기준 활성 시간’처럼 측정 방식이 드러나는 이름을 쓴다. 목표 관련 판정과 카테고리 합계를 구분하고 두 화면의 값이 다른 이유를 설명한다. |

| P1 | 레코더의 오류 필드는 있지만 활동 화면·트레이의 기록 상태에는 반영되지 않는다. 저장 실패 중에도 ‘기록 중’으로 보일 수 있다. | ‘관찰 중’과 ‘저장 정상’을 구분하고 마지막 저장 성공 시각과 지속되는 오류를 표시한다. 오류 해제는 저장 성공을 기준으로 한다. |
| P2 | 활동 화면에 요약·타임라인·상위 앱·상위 사이트·구간 표·자동 세션·장기 통계가 길게 이어진다. 기존 이미지에는 데이터가 적은 표의 빈 공간도 크다. | 기본 화면은 요약·타임라인에 집중하고 상세 표와 장기 통계를 탭 또는 접기 영역으로 이동한다. 표 높이를 행 수에 맞추고 정정 결과를 명확히 알린다. |
| P2 | 90% 등 신뢰도는 코드에 정한 규칙값이다. 사용자에게 검증된 정답률로 읽힐 수 있다. | ‘규칙 기반 확신도’임을 설명하거나 단계 표현을 사용한다. 실제 라벨 검증 전에는 확률적 정확도로 해석되지 않게 한다. |
| P2 | Python/uv 설치와 브라우저 확장 개발자 모드 로딩이 필요하다. | 핵심 결함 수정 후 설치·제거 가능한 배포판과 브라우저 연결 진단을 제공한다. 첫 실행부터 기록 확인까지 실제 신규 사용자 흐름을 검증한다. |

## 권장 진행 순서

1. **동의 적용 보장:** 실행 중 철회와 재개 동작을 수정하고 회귀 검증한다.
2. **데이터 일관성:** 자동 세션 저장·내보내기 경로를 통합하고 자정 집계·카메라 커버리지를 수정한다.
3. **제품 경험:** 홈 요약과 지표 용어를 정리하고, 저장 오류 표시와 비동기 통계를 구현한다.
4. **실사용 검증:** 코딩·강의·독서·회의·다중 모니터·자리 비움 시나리오에서 사용자 라벨과 비교한다. 미분류 비율, 잘못된 이탈 판정, 정정 빈도, 복귀 시간 오차를 보고한다.
5. **배포 검증:** 새 Windows 사용자 환경에서 설치·첫 기록·브라우저 연결·일시정지·내보내기·삭제·제거까지 확인한다.

휴대폰 감지·감정 관찰 등 새 센서 기능은 위 검증 이후에 판단하는 것이 좋다.

## 실행한 검증과 한계

- `ruff check .`: 통과.
- `node --test "browser_extension/test/*.test.js"`: 8개 통과.
- `python -m pytest -q --basetemp .pytest_audit_20261020 --tb=short`: **201개 통과, 2개 실패**. 두 실패는 현재 환경의 HKCU 레지스트리 쓰기 접근 거부(`WinError 5`)다.
  - `test_autostart_entry_roundtrip_in_a_private_key`
  - `test_install_registers_both_browsers_and_binds_the_data_folder`
- 첫 pytest 실행은 기본 임시 폴더 접근 제한으로 셋업이 실패했다. 작업 폴더 안의 전용 임시 경로로 바꿔 위 결과를 얻었다. pytest 캐시 쓰기 경고도 있었다. 이 환경 제한을 제품 결함으로 계산하지 않았다.
- 위 5개 결함은 기존 테스트와 별도로 메모리 DB·모의 센서로 재현했다. 기존 테스트 통과가 이 경계 조건들을 보장하지는 않는다.
- 기존 [성능 기록](performance.md)은 참고 자료이며 이번에 장시간 측정을 다시 수행한 결과가 아니다.
